# Guest Routing and Mobile Stability Design

## Goal

Keep the existing invitation experience and static Cloudflare Pages architecture while making guest data maintainable, sending unknown URLs to the generic Honored Guest invitation, and reducing crash risk on mobile Safari.

This work is a stability pass, not the planned visual redesign. It must not deploy or modify the live Cloudflare Pages project.

## Scope

The implementation will:

- Use `src/utils/guests.ts` as the only guest roster and lookup source.
- Preserve manually managed guest membership. There will be no opt-out flag, filtering system, or administration UI.
- Preserve the supported hyphenated and compact URL aliases generated from each guest name.
- Redirect unknown routes to `/`, the generic Honored Guest invitation.
- Reduce animation, particle, compositing, and decoded-image pressure on narrow screens and for visitors who prefer reduced motion.
- Add deterministic cleanup for long-lived browser resources.
- Keep the RSVP request and Google Apps Script integration unchanged.

The implementation will not:

- Deploy to Cloudflare Pages.
- Add Cloudflare Functions, SSR, authentication, or a database.
- Redesign the page, remove its gallery, remove music, or replace its visual identity.
- Add guest opt-out behavior beyond the owner manually editing the canonical roster.

## Guest Data Architecture

`GUESTS_DATA` in `src/utils/guests.ts` remains the canonical roster. Server-rendered Astro props provide the resolved guest name and role to the hero, entourage roster, and RSVP form.

The duplicated `GUESTS_MAP`, fuzzy matching, path parsing, and DOM synchronization code in `HeroSection.astro` and `RSVPModal.astro` will be removed. Known personalized routes already receive the correct `GuestInfo` at build time, so browser-side reconstruction is unnecessary.

Route aliases will be generated by a shared utility in `guests.ts`. The utility will normalize accented characters before producing aliases so `Lara Española` keeps `/lara-espanola` and never produces `/LaraEspaola`. Aliases that normalize to the same case-insensitive path will be deduplicated.

Removing a person from `GUESTS_DATA` manually will naturally remove that person's generated pages and roster entry on the next build. No additional removal logic will exist.

## Unknown Route Behavior

The static build will include a top-level `404.html`. It will use an immediate client redirect and a no-script fallback link to send visitors to `/`.

Cloudflare Pages currently treats the deployment as a single-page application because no top-level `404.html` exists. An unknown path therefore receives the root document under the unknown URL, after which the duplicated client path parser invents a guest name. Adding the explicit 404 page and removing client path parsing makes unknown routes deterministic: they resolve to the generic landing URL instead of synthesizing a guest.

The fallback will stay static and will not require a Pages Function.

## Performance Profile

A small pure utility will determine one of three rendering profiles:

- `full`: desktop-sized viewport with ordinary motion preferences.
- `mobile`: viewport width below 768 CSS pixels.
- `reduced`: `prefers-reduced-motion: reduce`, which takes priority over viewport width.

The utility will expose explicit budgets for star count, starfield frame rate, handwriting particles, and confetti particles. The same profile names will be placed on the root document as CSS classes so JavaScript and CSS use one policy.

Initial budgets:

| Effect | Full | Mobile | Reduced |
| --- | ---: | ---: | ---: |
| Starfield | 80 stars, 60 fps | 20 stars, 20 fps | Static frame |
| Handwriting sparkle | Existing density | 40% density | Text reveal without particles |
| Acceptance confetti | 180 particles | 40 particles | Disabled |

These values preserve the visual character on an iPhone 13 while leaving room for future lightweight effects. Future continuous effects should consume the same profile rather than creating independent, unbounded animation loops.

## Resource Lifecycle

The starfield will keep a single animation-frame loop. It will pause on `visibilitychange`, cancel its pending frame on `pagehide`, remove its resize and visibility listeners during teardown, and avoid restarting after teardown.

The handwriting reveal will retain animation-frame and timeout identifiers so unfinished work can be cancelled on `pagehide`. Particle arrays and canvas backing stores will be cleared after the reveal finishes or is cancelled.

The background audio element and fade interval will be retained by one controller rather than an untracked local variable. The fade interval will always clear when complete, and audio will pause and release its source on page teardown.

The countdown interval will stop once the event time has passed and on `pagehide`.

Scroll-driven navigation updates will use passive listeners and at most one scheduled animation-frame callback per frame.

## Image and Preloader Memory

The preloader will wait only for eager, above-the-fold images. It will not attach unresolved load listeners to every lazy gallery image. Its progress interval, fallback timeout, and image listeners will all be cleared when the preloader finishes.

The gallery will continue to use Astro-generated WebP thumbnails and HD lightbox images. Closing the lightbox will remove the HD image `src` and `onload` handler after the close transition, allowing Safari to reclaim the decoded image. Switching between images will clear the prior handler before assigning a new source.

The existing image collection and visible layout will not change in this pass.

## Mobile Compositing

Narrow-screen CSS will reduce GPU-heavy compositing without changing content structure:

- Repeated cards will use opaque or translucent backgrounds without `backdrop-filter` where the blur is not essential.
- Large decorative ambient layers will be hidden on mobile and reduced-motion profiles.
- Expensive shadows and filters on repeated gallery items will be simplified.
- Reduced-motion visitors will not receive looping or particle animations.

The hero remains visually prominent, and its core photograph, typography, gold accents, reveal interaction, and music remain present.

## Error Handling

Missing canvas contexts will disable the corresponding effect instead of throwing. Cleanup routines will be idempotent so multiple lifecycle events are harmless. Media playback failures will leave the invitation usable and will not create retry loops.

The existing Google Sheets `no-cors` submission behavior is explicitly out of scope and will remain unchanged.

## Testing and Verification

Tests will cover:

- Canonical guest lookup and normalized aliases, including `Lara Española`.
- Alias deduplication.
- Full, mobile, and reduced rendering-profile budgets.
- Production output containing a `404.html` that redirects to `/`.
- Production output containing personalized pages for names in `GUESTS_DATA`.
- Production output not containing the malformed `/LaraEspaola` route.

Behavior changes will follow a red-green cycle before implementation. Final verification will run the focused tests, `astro check`, and `astro build` sequentially. The site will be exercised through Astro's background development server on a known guest route and an unknown route. No deployment command will be run.

## Success Criteria

- Guest names and roles have one source of truth.
- `/lara-espanola` builds successfully without a malformed accented-name alias.
- Unknown deployed paths navigate to `/` and display the generic Honored Guest invitation.
- Mobile and reduced-motion profiles have deterministic animation budgets.
- Continuous loops, timers, image listeners, HD lightbox images, and audio have cleanup paths.
- The invitation retains its current content and visual identity.
- Focused tests, Astro diagnostics, and the static production build pass locally.
